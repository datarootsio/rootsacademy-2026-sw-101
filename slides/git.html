Section 1

Why version control

You have already invented a worse Git

report.py
report_v2.py
report_v2_charlotte.py
report_v2_charlotte_FIXED.py
report_final.py
report_final_v3.py
report_final_v3_USE_THIS.py
report_old_DO_NOT_DELETE.py

Which one runs in production? Who changed the tax rate, and why?

  • You cannot tell what changed between two of these without reading both.
  • Two people cannot edit safely – one of you loses work.
  • Nothing records why anything changed.

What a version control system gives you

You getWhich means
Full history of every fileGo back to any past state, exactly, in seconds
A reason attached to each changegit log and git blame answer "why is this line here?"
Parallel lines of workFour people, four features, one codebase, no stepping on toes
A review gateNothing reaches main without another pair of eyes
A distributed copyEvery clone is a full backup. Your laptop dying is an inconvenience, not a disaster

Git was written by Linus Torvalds in 2005, in ten days, because the Linux kernel team lost access to the tool they were using. It is distributed by design: there is no central server that Git itself needs. GitHub is a convention, not a requirement.

Section 2

The model

A commit is a snapshot with a name

Git does not store diffs. Each commit records the complete state of the project, plus:

  • who made it and when
  • a message
  • a pointer to its parent commit

The name is a SHA-1 hash of all of that, so it is unique and tamper-evident. Change anything and you get a different commit.

Diffs are computed when you ask for them. That is why git log is fast and history never drifts.

$ git show --stat a3f9c21
commit a3f9c21e4b8d0f7a2c5e9b1d3f6a8c0e2b4d6f81
Author: Charlotte De Baere <cdb@example.com>
Date:   Tue Sep 9 14:02:11 2026 +0200

    Fix VAT rate for Belgian invoices

 src/invoice.py | 4 ++--
 tests/test_invoice.py | 12 ++++++++
 2 files changed, 14 insertions(+), 2 deletions(-)

Four places your code lives

  working tree        staging area        local repo         remote
  (your files)        (the index)         (.git)             (GitHub)
       │                    │                  │                 │
       │──── git add ──────▶│                  │                 │
       │                    │─ git commit ────▶│                 │
       │                    │                  │─── git push ───▶│
       │                    │                  │◀── git fetch ───│
       │◀───────── git checkout / restore ─────│                 │
       │◀──────────────── git pull  =  fetch + merge ────────────│
  • Working tree – the files you edit. The only place with unsaved work.
  • Staging area – the changes you have chosen to include in the next commit.
  • Local repo – every commit you have ever made, in .git/.
  • Remote – the shared copy your team pulls from.

Why staging exists

Because one editing session usually produces two unrelated changes, and they deserve two commits.

Staging lets you commit the bug fix now and keep the half-finished refactor in your working tree.

git add -p walks you through your changes chunk by chunk and asks what to stage. It is the single best habit in this deck.

$ git status --short
 M src/invoice.py      ← bug fix, ready
 M src/report.py       ← experiment, not ready

$ git add src/invoice.py
$ git commit -m "Fix VAT rate for BE invoices"

$ git status --short
 M src/report.py       ← still yours to finish

A branch is a sticky note on a commit

                                    ┌── feature/invoice-vat
                                    ▼
                        (D) ─── (E)
                       ╱
  (A) ─── (B) ─── (C)
                    ▲
                    └── main          HEAD ──▶ feature/invoice-vat

A branch is a 41-byte file containing one commit hash. That is genuinely all it is – which is why creating one is instant and free.

Commit on a branch and the note moves forward to the new commit.

HEAD is "where you are now" – normally a pointer to the branch you are on.

HEAD the current commit
HEAD~1 its parent
HEAD~3 three back
main tip of main
Section 3

The daily loop

Set this up once, on every machine you use

$ git config --global user.name "C De Baere"
$ git config --global user.email "cdb@dr.io"

$ git config --global init.defaultBranch main
$ git config --global pull.rebase true
$ git config --global core.editor "code --wait"

$ git config --list --show-origin
  • The name and email are stamped into every commit you make, permanently. Use the address your GitHub account uses, or your commits will not be linked to you.
  • pull.rebase true keeps history linear instead of littering it with "Merge branch 'main' into main" commits.

--global writes to ~/.gitconfig. Drop the flag inside a repo to override it for that project only – useful for a client email address.

Starting: clone if it exists, init if it does not

joining an existing project 
$ git clone git@github.com:roots/academy.git
$ cd academy
$ git status
On branch main
Your branch is up to date with 'origin/main'.
starting from nothing 
$ mkdir my-project && cd my-project
$ git init
Initialized empty Git repository in
  /my-project/.git/

$ git remote add origin git@github.com:me/p.git
$ git push -u origin main

Everything Git knows lives in the .git/ directory. Delete it and you have an ordinary folder with no history. Copy the folder and you copy the whole history with it.

git status before and after everything

When you do not know what to do next, run git status. It tells you where you are and suggests the command.

  • Untracked – Git has never seen this file.
  • Modified – changed since the last commit, not staged.
  • Staged – will go into the next commit.
$ git status
On branch feature/invoice-vat
Changes to be committed:
  (use "git restore --staged <file>..." to unstage)
        modified:   src/invoice.py

Changes not staged for commit:
  (use "git add <file>..." to stage changes)
        modified:   src/report.py

Untracked files:
        notes.txt

The loop itself

$ git switch -c feature/invoice-vat

# ... edit files ...

$ git status
$ git diff
$ git add src/invoice.py
$ git commit -m "Fix VAT rate for BE invoices"

$ git push -u origin feature/invoice-vat
  • git diff – what you changed but have not staged.
  • git diff --staged – what is about to be committed. Read this before every commit.
  • git add . stages everything, including the debug print you forgot. Prefer naming files, or git add -p.
  • -u on the first push links your local branch to the remote one, so later you can just say git push.

Closes #418
  • Subject line under 50 characters, imperative mood: "Fix", "Add", "Remove" – it completes the sentence "this commit will…".
  • Blank line, then a body explaining why, not what. The diff already shows what.
  • One logical change per commit. If your message needs the word "and", split it.

You are writing for yourself in eight months, staring at a line you do not recognise, on a Friday afternoon.

Reading history

$ git log --oneline --graph --all -10
* a3f9c21 (HEAD -> feature/vat) Fix VAT rate
* 7b21d04 Add invoice rounding test
| * 4e8a1f2 (main) Bump pandas to 2.2
|/

$ git log --oneline -- src/invoice.py
$ git log -S "VAT_RATE"    # touches that text
$ git show a3f9c21
$ git blame src/invoice.py
$ git diff main..feature/vat

--oneline --graph --all is the only log invocation worth memorising. Make it an alias:

$ git config --global alias.lg \
  "log --oneline --graph --all -20"
$ git lg

git blame shows who last touched each line and in which commit. Not for assigning fault – for finding the commit message that explains the line.

.gitignore: what must never be committed

.gitignore 
# Python

.ipynb_checkpoints/

# Secrets – the important part
.env
*.pem

# OS and editor noise

# Data
data/raw/
  • Secrets. Once a key is pushed it is public and must be rotated, even if you delete it in the next commit.
  • Generated files. Virtual environments, caches, build output – anyone can regenerate them, and they cause conflicts nobody can resolve.
  • Large data. Git keeps every version of every file forever.

.gitignore does not apply to already-tracked files. If you committed it once, ignoring it later changes nothing:

git rm --cached .env
Section 4

Branching workflow

The workflow you will use at every client

  1  git switch main                     start from a known-good state
  2  git pull                            get everyone else's work
  3  git switch -c feature/short-name     your own line of work
  4  edit → git add → git commit          small commits, often
  5  git push -u origin feature/...       share it
  6  open a pull request                  ask for review
  7  address comments, push again         the PR updates itself
  8  merge (squash), delete the branch    main stays clean
  9  git switch main && git pull          back to step 1
  • main is always deployable. Nobody commits to it directly.
  • One branch per unit of work, and it lives for days, not weeks.
  • Every change reaches main through a reviewed pull request.
  • Today: your personal branch is your line of work. Push there, open a PR against main.

Branch commands

$ git branch                  # local branches
$ git branch -a               # plus remotes

$ git switch -c feature/vat     # create + go
$ git switch main               # go
$ git switch -                # previous branch

$ git branch -d feature/vat   # delete (merged)
$ git branch -D feature/vat   # delete anyway
$ git branch -m new-name      # rename current

switch and restore replaced the overloaded checkout in Git 2.23. checkout still works and you will see it everywhere – but it did three unrelated jobs, which is why it was so easy to lose work with.

git switch → move between branches
git restore → throw away file changes

Name branches so a stranger can guess the content: feature/invoice-vat, fix/null-customer-id, chore/bump-pandas.

origin, tracking, and what pull really does

$ git remote -v
origin git@github.com:roots/academy.git (fetch)
origin git@github.com:roots/academy.git (push)

$ git fetch          # download, change nothing
$ git status
Your branch is behind 'origin/main' by 3.

$ git pull             # fetch + integrate
$ git push

origin is just the default nickname for the remote you cloned from.

origin/main is a local, read-only bookmark of where main was on the server the last time you fetched. It does not update by magic.

git fetch is always safe – it never touches your files. When you are unsure of the state of the world, fetch first, then look.

Merging: two shapes

fast-forward – main did not move 
before:  A─B─C          (main)
              ╲
               D─E       (feature)

after:   A─B─C─D─E       (main, feature)

Git just slides the main pointer forward. No merge commit, perfectly linear.

three-way – both moved 
before:  A─B─C─F─G       (main)
              ╲
               D─E       (feature)

after:   A─B─C─F─G───M   (main)
              ╲       ╱
               D─────E

M is a merge commit with two parents. Git works out the combination from the common ancestor C.

On GitHub you will usually pick squash and merge: your branch's commits become one commit on main. Messy local history, clean project history.

Keeping your branch current

merge main into your branch 
$ git switch feature/vat
$ git fetch
$ git merge origin/main

A─B─C─F─G      (main)
      ╲     ╲
       D─E───M  (feature)
or rebase onto it 
$ git switch feature/vat
$ git pull --rebase origin main

A─B─C─F─G          (main)
          ╲
           D'─E'   (feature)

Merge is honest and never rewrites anything, at the cost of a knotty graph.

Rebase replays your commits on the new base: linear history, but new commit hashes – so only rebase work nobody else has pulled.

The golden rule

Rewrite history freely on a branch that is yours alone. Never rewrite history that someone else has pulled.

Safe to rewrite

  • Commits still only on your laptop.
  • Your own feature branch, pushed but not shared – force-push with --force-with-lease.

Never rewrite

  • main, develop, release branches.
  • Any branch a colleague has based work on.

git push --force overwrites the remote branch with yours, deleting commits other people pushed in the meantime. --force-with-lease refuses if the remote moved since your last fetch. Make it a habit; it costs nothing and has saved entire afternoons.

Section 5

Conflicts

A conflict is Git refusing to guess

It happens when two branches changed the same lines of the same file, and Git has no way to know which version is right.

  • Different files? No conflict.
  • Different parts of one file? Usually no conflict.
  • Same lines? Your call.

Conflicts are not a failure. They are a question. Nothing is broken and nothing is lost while you answer it.

$ git merge origin/main
Auto-merging src/invoice.py
CONFLICT (content): conflict in src/invoice.py
Automatic merge failed; fix conflicts and then
commit the result.

$ git status
You have unmerged paths.
  (fix conflicts and run "git commit")
Unmerged paths:
        both modified:   src/invoice.py

Reading the markers

def total(amount):
<<<<<<< HEAD
    return amount * 1.21
=======
    return round(amount * 1.06, 2)
>>>>>>> origin/main
<<<<<<< HEADyour version starts
=======the divider
>>>>>>> origin/maintheir version ends

Your job: delete all three marker lines and leave the code you want – theirs, yours, or a combination. Often the right answer is neither.

Search for <<<<<<< before you commit. A marker left in a file is a syntax error you will find in CI, in front of everyone.

Resolving, step by step

$ git status                    # which files?
$ git diff                    # see both sides

# ... edit each file, remove markers ...

$ python3 -m pytest           # still working?
$ git add src/invoice.py      # mark resolved
$ git status                  # anything left?
$ git commit                  # finish the merge

# changed your mind at any point:
$ git merge --abort
  • git add is how you say "resolved". Until then the merge is paused.
  • git merge --abort puts everything back exactly as it was. It always works while the merge is unfinished.
  • Run the tests before committing the merge. A resolution that compiles is not necessarily correct.

Taking one side wholesale:

git checkout --ours <file>
git checkout --theirs <file>

Section 6

Recovery

Two questions get you to the right command

Where is the change now, and has anyone else seen it?

The change isUndo it with
edited, not stagedgit restore <file>
staged, not committedgit restore --staged <file>
committed, not pushedgit commit --amend, or git reset --soft HEAD~1
pushed, on your own branchrewrite, then git push --force-with-lease
pushed, and someone has pulled itgit revert <commit> – never rewrite
gone, and you cannot find itgit reflog

Before any of them: git status, then git log --oneline -5. Ten seconds of looking saves an hour of undoing your undo.

Not committed yet

"I want my edits gone" 
$ git restore src/invoice.py     # one file
$ git restore .                  # everything

# unstage but keep the edits
$ git restore --staged src/invoice.py

# also delete new untracked files
$ git clean -n                 # dry run first
$ git clean -fd

git restore is the one destructive command with no undo. Uncommitted work has never been recorded anywhere, so Git cannot bring it back. git clean -fd is the same, for files Git has never seen.

Always run git clean -n first and read the list.

Not sure you want to lose it? git stash instead – it costs nothing and it is reversible.

git stash: put it down and pick it up later

$ git stash push -m "half-done VAT refactor"
Saved working directory and index state

$ git switch main      # clean tree, free to go
# ... fix the urgent thing ...

$ git switch feature/vat
$ git stash list
stash@{0}: On feature/vat: half-done refactor

$ git stash pop          # restore + remove
$ git stash apply       # restore, keep a copy
$ git stash drop

The everyday use: you are mid-thought and someone needs a hotfix on main.

  • Always pass -m with a message. stash@{3} on Thursday means nothing to you.
  • git stash push -u also stashes untracked files.

The stash is a drawer, not a filing cabinet. Work left there gets forgotten and never shows up in git log. If it will take more than an hour, make a commit on a branch instead.

"That commit was wrong": --amend

# bad message
$ git commit --amend -m "Fix VAT for BE"

# forgot a file
$ git add tests/test_invoice.py
$ git commit --amend --no-edit

# already pushed the branch?
$ git push --force-with-lease

--amend does not edit the last commit. It replaces it with a new one – new hash, old commit orphaned.

Only amend the tip of your own unshared branch. Amending something a colleague has pulled gives them a duplicate history and a bad afternoon.

Amending the commit that is already on main: don't. Make a new commit.

--hard is the one that hurts. It discards uncommitted work with no record. Everything else on this slide is recoverable through the reflog.

revert: undo in public

$ git log --oneline -3

"I committed to main by accident"

you have not pushed yet 
$ git log --oneline -2
a3f9c21 (HEAD -> main) Fix VAT rate
c19b7e5 (origin/main) Initial layout

# 1. save the work on a proper branch
$ git switch -c feature/invoice-vat

# 2. put main back where the remote is
$ git switch main
$ git reset --hard origin/main

# 3. carry on
$ git switch feature/invoice-vat

The branch is a pointer, so this is just moving a sticky note. Your commit is still there, now on a branch with a name.

Already pushed to main? Do not force-push. Revert it in the open and move on:

git revert a3f9c21
git push

Most teams protect main on GitHub so this cannot happen. If you can push straight to main, ask why.

git reflog: the undo history for your undos

$ git reflog
5d0c8e3 HEAD@{0}: reset: moving to origin/main
a3f9c21 HEAD@{1}: commit: Fix VAT rate
7b21d04 HEAD@{2}: checkout: moving to main
4e8a1f2 HEAD@{3}: commit: Experiment I deleted

$ git switch -c rescue a3f9c21
# or, to put the branch back:
$ git reset --hard HEAD@{1}

Git logs every move HEAD makes, locally, for 90 days.

Bad reset, bad rebase, deleted branch, wrong amend – the commit is still in .git. The reflog is how you find its hash again.

If you have committed it, you can get it back. That is the sentence to remember from this whole section.

The exception, again: work you never committed.

cherry-pick: I want that one commit, here

$ git log --oneline feature/experiment
9f2a7c1 Refactor everything
8e1b3d4 Fix the typo in the error message

$ git switch main
$ git cherry-pick 8e1b3d4
[main 2c7f9a0] Fix the typo in the message

before:  A─B          (main)
          ╲
           C─D        (experiment)

after:   A─B─D'       (main)
          ╲
           C─D        (experiment)

Copies the change from one commit onto your current branch as a new commit.

  • Useful for a hotfix that needs to land on a release branch too.
  • Not a substitute for merging. Cherry-picking half a branch leaves you with two copies of the same change and a confusing history.
  • Conflicts are resolved exactly like a merge, then git cherry-pick --continue.

"I committed a secret"

Rotate the credential first. Everything else is secondary.

  1. Revoke and reissue the key. Pushed history is public, cached and mirrored.
  2. Tell whoever owns the system. Quietly deleting it turns an incident into a breach.
  3. Then clean the history, force-pushing with the team's agreement.
  4. Add it to .gitignore and move the value to an environment variable.
only just committed, nothing pushed 
$ git rm --cached .env
$ echo ".env" >> .gitignore
$ git commit --amend --no-edit
already in older commits 
$ pipx install git-filter-repo
$ git filter-repo --invert-paths --path .env
$ git push --force-with-lease --all

Every colleague must re-clone: every hash changed.

Two more worth knowing exist

rebase -i – tidy up before review 
$ git rebase -i HEAD~4

pick 7b21d04 Add rounding test

squash 9f2a7c1 fix typo again
reword a3f9c21 Fix VAT rate

Turn six "wip" commits into one reviewable change. Your branch only.

bisect – find the commit that broke it 
$ git bisect start
$ git bisect bad                # now
$ git bisect good v1.4.0        # then

# Git checks out the midpoint; you test
$ git bisect good     # or bad
# ... repeat ~log2(n) times ...

a3f9c21 is the first bad commit
$ git bisect reset

400 commits, 9 tests. Binary search on history.

Two more games

Git golf

A target repository state is described. Reach it in the fewest commands. Everyone reveals their solution at the same time.

  • Fewest commands wins; ties broken by clearest history.
  • Nine holes, increasing in difficulty.

Blame detective

A repository with 40 commits and one bug. Find, using only Git, who introduced it, when, and what they thought they were fixing.

  • git log -S, git blame, git bisect, git show.
  • Write your answer as a three-line incident note.
