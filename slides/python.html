What happens between your file and the CPU

import dis

def total(prices):
    return sum(p * 1.21 for p in prices)

dis.dis(total)
bytecode, abridgedLOAD_GLOBAL sum LOAD_CONST <genexpr> MAKE_FUNCTION CALL 1 RETURN_VALUE
  • CPython compiles your source to bytecode – that is what __pycache__ holds – and a loop written in C runs it. That loop is the "Python is slow" you have heard about.
  • The GIL lets one thread run bytecode at a time. Threads help while you wait on a network or a disk, never with arithmetic. For CPU work, use processes.
  • numpy and polars are fast because one instruction hands a whole array to compiled code. Keep the inner loop out of Python, not Python out of your program.

Scope: what a function can see

counter = 0            # module level

def bump():

Indexes start at 0. The last item is at len(nums) - 1, or just -1.

Negative indexes count from the right. nums[-1] is how Python spells "the last one" – you will never write nums[len(nums) - 1] again.

Slicing: [start:stop:step]

nums = [1, 2, 3, 4, 5, 6]

nums[1:3]     # [2, 3]      stop is excluded
nums[:3]      # [1, 2, 3]   from the start
nums[3:]      # [4, 5, 6]   to the end
nums[0:5:2]   # [1, 3, 5]   every second
nums[::-1]    # [6, 5, 4, 3, 2, 1]  reversed
nums[:]       # a shallow copy

nums[10:20]   # []  slices never raise

Read [1:3] as "from index 1, up to but not including 3". Same rule as range.

Slicing works on anything ordered – lists, tuples, strings:

"hello"[1:4] # 'ell'

A slice returns a new list. An index returns the item itself.

Inheritance: a Student is a Person

class Student(Person):

        return f"{base}, grade {self.grade}"

super().__init__(...) runs the parent's setup so you do not repeat it. Forget it and self.name will not exist.

  • Raising something the parent never raised, or narrowing the arguments.

Two of the five are really one habit each: separate the stages (S, O) and pass in what you use (I, D). L is a warning about inheritance.

The other side of the ledger

You over-applied them when

  • An interface has exactly one implementation and no test double.
  • Classes are named ...Manager, ...Helper, ...Handler, ...Factory – names that describe no thing.
  • Adding one field means editing four files.
  • There is a config flag for behaviour nobody has ever switched.
  • You must open three files to follow one request.

You under-applied them when

  • There is a function you are afraid to change.
  • A test needs the network, a real database, or the right day of the month.
  • The same fix has to be applied in three places, and someone always misses one.
  • Two people cannot work on the file at once without a conflict.
  • New joiners ask the same question about the same function every time.

The honest default: write it plainly, add structure at the second or third real reason, and delete the abstractions that never paid for themselves. Every abstraction charges the reader one jump; make it earn that.

Writing your own context manager

as a class 
class FileManager:

        return self.file

        self.file.close()

from contextlib import contextmanager

@contextmanager

        today=date.today() - timedelta(days=1),
    )

    write_report(result.totals, settings.output)
    log.info("%s rejected rows", len(result.rejected))
    return 1 if result.rejected else 0

main() is the only function that knows about HTTP, the clock, the filesystem and the environment. Everything above it takes what it needs as an argument – so everything above it is testable with literals.

Section 13

Craft

PEP 8, in the six rules that matter

  • Four spaces per indent level. Never tabs.
  • Lines under ~88 characters.
  • snake_case for functions and variables, PascalCase for classes, UPPER_SNAKE for constants.
  • Two blank lines between top-level definitions, one between methods.
  • Spaces around operators and after commas – x = f(a, b), not x=f(a,b).
  • Imports at the top, one per line, grouped stdlib / third party / local.

What a reviewer is actually looking for

In your code

  • Can I tell what this does from the names, without the diff's description?
  • What happens on the unhappy path – bad input, a timeout, an empty file?
  • Which part of this would I have to change when the requirements move? Is it one part?
  • Is anything here already in the standard library?
  • Could this function be tested without a network, a clock or a file?

In your pull request

  • One change per pull request. A refactor and a feature in one diff is unreviewable.
  • A description that says why, since the what is in the diff.
  • A test that fails without your change.
  • No commented-out code, no print debugging, no TODO without a name on it.

Review your own diff first, in the web interface. You will find a third of the comments yourself, and the reviewer gets to spend their attention on the other two thirds.
